# 修復紀錄維護

目的：這份文件的主要讀者是**使用者本人**——寫的時候要想著「這個人想從這次修改裡學到什麼」，不是單純留一份技術備忘給下一個 Claude session。解釋給使用者聽的「怎麼修的」如果只留在對話紀錄裡，之後就查不到、也複習不到；這個 skill 把每次修 bug／UX 改善的根因、修法、以及修法背後可以遷移到其他情境的通用觀念，同步寫成 `FIX_NOTES.md`（專案根目錄）裡的一個條目。

跟 [`commit-convention`](../commit-convention/SKILL.md) 的差異：commit message 是給 git log 看的、跟著每次 commit 走、篇幅要精簡；`FIX_NOTES.md` 是給使用者看的學習筆記，可以完整解釋根因、修法選擇、背後的原理，不受 commit message 篇幅限制。兩者不互相取代，一次修改通常兩者都該寫。

## 什麼時候該寫一筆

- 修好一個真的會影響使用者的 bug（不是型別錯誤那種寫完馬上會被 compiler/lint 擋下來的）。
- 做了一項 UX／互動行為的改善，且改法不是一眼就能看懂「為什麼要這樣做」（例如繞過某個瀏覽器行為、處理某個 race condition、選了某個做法是因為排除了另一個做法）。
- 使用者明確要求記錄。

單純的樣式微調、文字修改、或改法本身淺顯到看 diff 就懂，不需要特別寫一筆——不要為了寫而寫，湊出來的條目只會稀釋掉真正有價值的內容。

## 條目格式

寫在 `FIX_NOTES.md` 檔案最上面那段簡介之後、既有條目之前（新的在上面，還是舊的在上面都可以，跟著這個檔案目前的排序方式走，不要自己突然改變順序邏輯）。每筆條目用二級標題 `## YYYY-MM-DD 這次改動的簡短主題`（同一天有多筆不相關的修改，可以用同一個日期標題、底下開多個三級小節，就像既有條目那樣）。

每個問題點用三級標題起頭，底下固定四段（**驗證方式**視情況可省略，但有做瀏覽器實測或寫測試驗證的話務必寫；**問題／修法／背後的通用觀念**這三段不可省略，是這份文件對使用者最有價值的部分）：

```markdown
### 這個問題的簡短標題

**問題**：使用者會遇到的實際現象是什麼，不是「程式碼寫錯了」這種空泛描述。

**修法**：根因是什麼、選擇了什麼修法、為什麼選這個修法（如果有排除掉的替代方案，值得提一句為什麼不選它）。技術細節要具體到看得出「改了什麼機制」，不是只複述 diff。

**背後的通用觀念**：這個修法用到的原理或模式，脫離這次的 bug 本身也成立、下次遇到類似情境還能再用上的知識——例如事件冒泡與 `stopPropagation()`、瀏覽器 `click` 事件的 target 是怎麼合成出來的、某個 race condition 的成因。用「教會使用者一個可遷移的概念」的角度寫，不是重複講一次上面「修法」段落已經講過的細節。如果這次的修法純粹是套用某個已知模式、沒有值得特別解釋的原理，可以直接說明這是哪個常見模式（例如「這是常見的 click-outside-to-close 模式」），不用硬掰。

**檔案**：改了哪些檔案，簡短註記每個檔案改了什麼部分。

**驗證方式**：怎麼確認修好了（瀏覽器實測步驟、單元測試、手動 curl 等），如果同時驗證了「沒有修過頭」（原本該有的行為還在），也要寫出來。
```

日期用 `YYYY-MM-DD`（today 的日期，不要用相對日期字眼）。文字風格比照這個專案既有文件（`PROGRESS.md`、`CLAUDE.md`）：繁體中文、技術細節寫具體、不加不必要的客套或形容詞——但「背後的通用觀念」這段例外，可以放慢步調、用類比或具體情境把原理講清楚，畢竟這段是寫給人學習用的，不是純技術備忘。

## 給模型的提醒

- 寫條目前，先讀一次 `FIX_NOTES.md` 目前的開頭簡介與最近幾筆條目，掌握這個檔案現有的語氣跟細節密度，新條目要跟舊的一致，不要突然換一種風格。
- 這份文件的價值在「根因」「為什麼選這個修法」「背後可遷移的觀念」，不是逐行翻譯 diff——寫之前先確認自己真的講得出「為什麼壞掉」，講不出來就代表根因還沒查清楚，不要硬寫。
- 「背後的通用觀念」段落是寫給使用者學習用的，下筆前想一下：如果使用者以後自己寫程式遇到類似情境，這段話能不能幫他認出「這跟之前那個 bug 是同一種問題」。寫得太抽象（例如只丟一個專有名詞不解釋）或太貼著這次的程式碼講（變成第二次複述修法）都沒有達到目的。
- 如果一次任務改了好幾個不相關的問題（像同時修三個獨立的 UX 問題），每個問題各自開一個三級小節，不要合併成一段講不清楚。
- 寫完 `FIX_NOTES.md` 條目後，也要照 [`commit-convention`](../commit-convention/SKILL.md) 正常寫 commit message；`FIX_NOTES.md` 的新增/修改本身通常跟著同一個 commit 一起進去（`docs` 或跟該次改動同一個 type 都合理，看是不是純文件變動）。
- 這個 skill 只負責維護 `FIX_NOTES.md` 本身，不負責決定要不要 commit／要不要開 PR——那是 `commit-convention`／`pr-prep` 的範圍。
