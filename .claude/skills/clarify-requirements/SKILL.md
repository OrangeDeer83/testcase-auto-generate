# 動手前先問清楚

目的：這個專案已經實際發生過「做完才發現方向不是使用者要的」的案例——2026-09-01，使用者說「想減少呼叫模型時的輸入量」，直接被理解成「加一個讓使用者手動勾選用例範圍的 UI」，整批功能做完、測試都過、也上線了，使用者才澄清真正要的是「系統自動判斷範圍，使用者不用做任何操作」，等於白做一次、還得把功能整批 revert 掉重做（見 FIX_NOTES.md「回覆澄清問題時，自動只把相關用例送給模型」那筆條目）。根因不是實作做錯，是「需求裡真正模糊的地方，在動手之前就該問，而不是做完才發現」。

## 什麼時候該問

- 使用者提出的需求本身帶有一種以上合理的解讀方式（例如「減少輸入量」可以是「使用者自己指定範圍」，也可以是「系統自動判斷範圍」——兩種都合理，但方向完全不同）。
- 使用者用抽象詞彙或簡短的一句話描述想法（「像 XX 一樣」「有沒有辦法做到 OOO」），沒有具體到能直接對應成單一實作方案。
- 需求牽涉到「誰觸發」「什麼時候觸發」「邊界情況怎麼處理」，而使用者的敘述沒有明確講到這些。
- 需求可能需要一個「猜錯了/資訊不夠時怎麼辦」的降級行為，而使用者沒有指定。
- 使用者對一個已經做完的東西提出修正，但修正本身的敘述還是有模糊空間——這時候格外容易因為「上一版做錯了、想趕快修正」而心急，反而更該先問清楚這次到底要往哪個方向修，不要又猜錯第二次。

## 什麼時候不用問

- 使用者的指令已經具體到只有一種合理實作方式（例如明確的文字修改、明確的檔名、明確的數值、明確指名要改的那一行程式碼）。
- 使用者已經在同一輪對話裡主動說明過這些細節，不需要重複確認。
- 使用者已經明確表示「不用問了，你決定」，或給過清楚的一次性授權。

## 怎麼問

- 用 AskUserQuestion 工具列出具體的選項與情境（不是開放式的「你想要什麼？」），附上每個選項的實際後果，讓使用者可以快速選擇或補充。
- 一次問完真正關鍵、會影響實作方向的問題，不要為了問而問、也不要瑣碎到每個小細節都要確認——這樣使用者才不會覺得每次提需求都要被盤問一輪。
- 使用者給的答案如果還是有模糊空間，繼續追問一輪，不要在還不確定的情況下就開始動手；寧可多問一輪，也不要做完才發現方向錯誤、需要整批 revert 掉重做。

## 給模型的提醒

- 這個 skill 的精神跟「LLM 不可以亂猜」的核心原則是同一件事的兩種層面：一個是產品裡的 LLM 不能亂猜測試用例內容，一個是我（Claude）自己在協助開發時也不能亂猜使用者的需求方向。
- 已經做完的功能如果事後發現方向錯了，不代表當初的猜測「合理」——事後合理化猜測是常見的陷阱。正確的反應是承認方向猜錯了，並且在下一次遇到類似模糊需求時，把這次沒問到的那個關鍵點記起來，下次主動先問。
